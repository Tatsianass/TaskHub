# План миграции сервера на Go (полное переписывание, rollback на каждом этапе)

Статус: черновик плана, код не написан. Оценки — для одного разработчика, в рабочих днях.

## 1. Что именно переписываем

Поверхность маленькая (измерено по `server/`):

| Часть | Объём |
|---|---|
| Исходники `server/src` | ~1 000 строк TS (Express 5 + `pg`) |
| Тесты `server/test` | ~2 100 строк, 15 файлов |
| Эндпоинты | 12: `/health`, `/auth/{register,login,apple,me,logout,account}`, `/tasks` (GET/POST/PUT/DELETE), `/birthdays` (то же), `/import` |
| Таблицы | `users`, `sessions`, `tasks`, `birthdays`, `schema_migrations` (3 миграции) |
| Внешние зависимости | PostgreSQL (`DATABASE_URL`, сейчас Supabase), JWKS Apple |
| Деплой | Fly.io, одна машина 256 МБ (`--ha=false`, rate limit в памяти) |
| Клиент | `src/lib/api.ts`, URL зашит в сборку (`EXPO_PUBLIC_API_URL`) |

Клиент не трогаем вообще: контракт (пути, JSON, коды ошибок `{ "error": "CODE" }`, статусы) остаётся
побайтно совместимым.

## 2. Ключевые решения (они и дают rollback)

1. **База общая, данные не копируем.** Go и Node работают с одним и тем же Postgres и одной схемой.
   Откат любого этапа = переключение трафика, без обратной миграции данных.
2. **Схема — это контракт.** Пока живут обе реализации, миграции только *expand/contract*:
   добавлять колонки/таблицы можно, удалять и переименовывать — нет. До этапа 9 миграции ведёт Node.
3. **Совместимость на уровне данных уже есть:** токены сессий хранятся как `sha256(token)` hex —
   живые сессии продолжают работать; пароли — scrypt `N=16384, r=8, p=1, keylen=64` с параметрами в JSONB
   (`golang.org/x/crypto/scrypt` читает их как есть); `id` — клиентские строки; время — BIGINT мс.
4. **Публичный хост не меняется** (`taskhub-api-tatianas.fly.dev` вшит в уже опубликованные билды).
   Канареечный трафик: Node остаётся на хосте и по флагу отдаёт `fly-replay: app=taskhub-api-go`
   (процент пользователей, стабильный хэш от токена). Финальный переход — `fly deploy` Go-образа в
   исходное приложение; откат — `fly deploy -i <образ Node>` (так уже делали при переезде на Postgres).
   *Проверить по документации Fly перед этапом 4: лимит размера тела для replay (у нас тело ≤ 1 МБ).*
5. **Black-box контрактный набор тестов** — главный страховочный механизм (этап 0). Один и тот же набор
   по HTTP гоняется против Node и против Go; Go принимается только при полном совпадении.
6. **Стек Go:** `net/http` (Go 1.22+ routing) + `pgx/v5` (pool) + `golang.org/x/crypto/scrypt` +
   `crypto/rsa` для JWT Apple (или `lestrrat-go/jwx`); без ORM. Сборка — multi-stage в `scratch`/distroless.

## 3. Где реально сложно (ловушки совместимости)

- **Валидация «как в JS».** `validation.ts` мягкая и со старыми клиентами: отсутствующее поле → `null`/`[]`/`'09:00'`/`true`,
  неизвестные поля отбрасываются, `trim()` в JS ≠ `strings.TrimSpace` в Go (разный набор пробелов, BOM),
  числа в JSON — `float64` (`createdAt` принимает не-целые, `remindOffsets` — только целые; `1.0` в JS это целое).
  Нужны `json.RawMessage` + собственные чекеры, а не `struct`-теги.
- **Паритет ошибок Express:** 413 `PAYLOAD_TOO_LARGE` (лимит 1 МБ), 400 `INVALID_JSON`, 404 `NOT_FOUND` для неизвестных
  путей, заголовок `Retry-After` на 429, CORS (`CORS_ORIGIN`), `trust proxy` → реальный IP для rate limit.
- **Тайминг логина.** Всегда считать scrypt, даже для неизвестного email (`DUMMY_HASH`); порядок 404/401 сохранить.
- **Rate limit в памяти.** Во время канарейки два процесса считают счётчики раздельно — лимиты фактически
  ослабляются до финального переключения. Приемлемо, но зафиксировать.
- **Sign in with Apple:** RS256, issuer/aud/exp, `nonce == sha256(rawNonce)` hex, кэш JWKS (TTL 1 ч, refetch ≥ 60 с),
  503 `APPLE_UNAVAILABLE` при недоступности ключей. Поведение `emailVerified` как `true` **или** `"true"`.
- **Транзакция `/import`:** all-or-nothing + идемпотентность + `remappedId` (SHA-256 `user\0id` → UUID-форма) — должно
  совпасть побитно, иначе повторный импорт создаст дубли.
- **Supabase и пулер.** Если `DATABASE_URL` указывает на pgbouncer в transaction-режиме: у `pgx` отключить кэш prepared
  statements (`default_query_exec_mode=simple_protocol` / `cache_describe`), а `pg_advisory_lock` для миграций
  в этом режиме не работает (нужен direct-коннект). **Неизвестно из репозитория — уточнить, какой URL в секретах Fly.**
- **BIGINT → число:** в Node парсер возвращает `Number`; в Go `int64` в JSON — числом, не строкой.

## 4. Этапы

Формат: цель → работы → критерий выхода → **rollback**. Каждый этап — отдельный PR/деплой, следующий не начинается,
пока не выполнен критерий выхода предыдущего.

### Этап 0 — Заморозка контракта и контрактные тесты (2 дня)
- Работы: вынести тесты в `contract/` — HTTP-only (`BASE_URL`, `TEST_DATABASE_URL` для схемы-на-прогон), покрыть все 12 эндпоинтов,
  все коды ошибок, легаси-тела старых клиентов, граничные значения валидации (порт из `validation.test.ts`, `copy.test.ts`,
  `import.test.ts`, `auth.test.ts`); сохранить golden-ответы; добавить в CI матрицу `target: node`.
- Выход: контрактный набор зелёный против Node в CI; список расхождений «баг или контракт» разобран (баги Node **не** чиним
  в этой миграции, фиксируем как контракт).
- Rollback: не требуется — прод не затронут.

### Этап 1 — Каркас Go, CI, пустой деплой (1 день)
- Работы: `server-go/` (или `go-server/`), `config` (те же env: `PORT, HOST, DATABASE_URL, PG_POOL_MAX, CORS_ORIGIN, TRUST_PROXY, APPLE_BUNDLE_IDS`,
  та же логика `sslmode`), `/health`, graceful shutdown (SIGTERM, 10 с), структурные логи без тел запросов;
  Dockerfile, `fly.toml` для **нового** приложения `taskhub-api-go`; job в CI (`go vet`, `go test`, контракт против Go).
- Выход: `taskhub-api-go.fly.dev/health` отвечает 200; трафика нет.
- Rollback: `fly apps destroy taskhub-api-go`.

### Этап 2 — Слой БД и проверка схемы (1 день)
- Работы: `pgx` pool с теми же таймаутами (`statement_timeout 10s`, `idle_in_transaction_session_timeout 15s`, connect 10s),
  `withTx`, репозитории `users/sessions/tasks/birthdays` 1:1 с TS-версией (все запросы фильтруют по `user_id`),
  маппинг SQLSTATE `23505`/`23514` (с именем constraint) в доменные ошибки. Go **не применяет** миграции: на старте только
  проверяет `max(schema_migrations.version) ≥ 3` и падает с понятной ошибкой, если схема старее/новее.
- Выход: репозиторные тесты (порт `repos-auth`, `db`, `copy`) зелёные на Postgres 16.
- Rollback: прод не затронут (нет трафика).

### Этап 3 — HTTP-инфраструктура и валидация (1,5 дня)
- Работы: роутер, CORS, лимит тела 1 МБ, единый обработчик ошибок `{ "error": CODE }`, 404/413/400-JSON, `requireAuth`
  (Bearer, `SESSION_EXPIRED` vs `UNAUTHORIZED` с удалением просроченной сессии), порт `validation.ts` (table-driven тесты
  на тех же векторах + fuzz/differential: одинаковые случайные тела в Node и Go → одинаковый вердикт).
- Выход: differential-прогон валидации — 0 расхождений на ≥ 10 000 сгенерированных тел.
- Rollback: прод не затронут.

### Этап 4 — Канарейка read-only: `GET /tasks`, `GET /birthdays`, `GET /auth/me` (1,5 дня)
- Работы: хэндлеры; в Node — middleware `fly-replay` за флагом `GO_REPLAY_PCT` и списком групп маршрутов
  `GO_REPLAY_ROUTES=reads` (стабильный хэш от `Authorization`); дополнительно **shadow-сравнение**: Node для части
  GET-запросов асинхронно вызывает Go через `.internal` и логирует diff тел (без персональных данных — только id/хэш и имена полей).
- Выход: 1 % → 10 % → 50 % → 100 % чтений по ≥ 24 ч на ступень; 0 diff в shadow; p95 не хуже Node; 5xx не выше базового.
- **Rollback:** `fly secrets set GO_REPLAY_PCT=0` (применяется за секунды рестартом) — все чтения снова в Node. Данные не затронуты.

### Этап 5 — Запись: tasks и birthdays, `/import` (2 дня)
- Работы: POST/PUT/DELETE для `/tasks` и `/birthdays` (409 `DUPLICATE_ID`, 404 для чужих id, 400 `INVALID_*`), `/import`
  в одной транзакции с `remappedId`. Реплей по группам: `writes`, затем `import`.
- Выход: контрактный набор зелёный против Go; ночной differential: один сценарий на двух изолированных схемах → одинаковые ответы
  и одинаковое итоговое состояние таблиц (дамп без `seq`/времени); канарейка 1 → 100 % с теми же ступенями.
- **Rollback:** `GO_REPLAY_ROUTES` без `writes`. Строки, созданные Go, нормально читаются Node (одна схема, те же ограничения).

### Этап 6 — Аутентификация: register/login/logout/account + rate limit (3 дня) — самый рискованный
- Работы: scrypt-совместимость, `DUMMY_HASH`, нормализация email (`trim().toLowerCase()`), 400/401/404/409 как в Node,
  rate limit (IP 30 / email 10 за 15 мин, `Retry-After`) с тем же поведением очистки, `DELETE /auth/account` (каскад в БД),
  hourly sweep просроченных сессий (в каждый момент его должен вести ровно один процесс — иначе безвредно, но лишний `DELETE`).
- Обязательные тесты: хэши, **сгенерированные настоящим Node-кодом** (фикстуры), проверяются в Go и наоборот (Go-хэши — в Node);
  замер времени «неизвестный email» vs «неверный пароль».
- Выход: контракт зелёный; канарейка: сначала `auth-read` (`/auth/me`, `/auth/logout`), затем login, затем register.
- **Rollback:** убрать группу из `GO_REPLAY_ROUTES`. Пользователи и сессии общие, повторный вход не нужен.

### Этап 7 — Sign in with Apple (1,5 дня)
- Работы: проверка JWT (RS256, iss/aud/exp/nonce), кэш JWKS, гонка двух параллельных входов (unique violation → победитель),
  правило «не привязывать Apple к существующему email» и заглушка `<sub>@apple.invalid`.
- Тесты: порт `apple.test.ts` (свои RSA-ключи, фиктивный JWKS); ручная проверка на TestFlight-билде на реальном устройстве.
- Выход: контракт + ручной вход через Apple на реальном устройстве через Go.
- **Rollback:** убрать группу `apple` из `GO_REPLAY_ROUTES`.

### Этап 8 — Полное переключение хоста (1 день работы + 14 дней наблюдения)
- Работы: `fly deploy` Go-образа в исходное приложение `taskhub-api-tatianas` (тот же `fly.toml`: порт 8080, `/health`, 1 машина);
  `taskhub-api-go` оставить, образ Node сохранить тегом `node-final` и записать в `fly releases`.
- Выход: 14 дней без инцидентов; `scripts/check-hosted-server.sh` зелёный; логи без `INTERNAL`.
- **Rollback:** `fly deploy -i <образ Node>` (минуты) — схема не менялась, данные те же.

### Этап 9 — Миграции переходят к Go (1 день)
- Работы: Go применяет миграции (тот же `schema_migrations`, тот же advisory lock id `727274`, прямой коннект), либо `goose`/`golang-migrate`
  с импортом существующей версии. Правило expand/contract остаётся, пока Node-образ нужен для отката.
- Выход: новая миграция проходит через Go-деплой; Node-образ всё ещё стартует на новой схеме.
- Rollback: Node-образ совместим со схемой (контракт expand/contract); сама миграция — только вперёд.

### Этап 10 — Вывод Node из эксплуатации (0,5 дня)
- Работы: удалить `taskhub-api-go`, `server/` (TS) переместить в тег `node-final`, обновить `deploy-server.yml`,
  `docs/PROJECT_OVERVIEW.md`, `specs/`.
- Rollback: после удаления — `git checkout node-final` + деплой из тега/образа; работает, пока схема остаётся обратно совместимой
  (после первого нетривиального contract-шага откат на Node заканчивается — это осознанная точка невозврата, фиксируется в записи).

## 6. Оценка трудозатрат

| Этапы | Дни работы |
|---|---|
| 0 контракт | 2 |
| 1 каркас | 1 |
| 2 БД | 1 |
| 3 HTTP/валидация | 1,5 |
| 4 чтения | 1,5 |
| 5 запись | 2 |
| 6 auth | 3 |
| 7 Apple | 1,5 |
| 8 переключение | 1 (+14 дней наблюдения) |
| 9–10 | 1,5 |
| **Итого** | **≈ 16 рабочих дней (~3 недели) + 2 недели soak** |

С активной помощью AI на написании кода и тестов — ориентир 8–10 дней; на сроки в основном влияют наблюдение
на каждой ступени канарейки и ручные проверки (Apple на устройстве), а не сам код.
